# Решения и отклонения от workflow

Формат записи: `Шаг N: <решение> — <причина>`.

Шаг 1: `LogFile.Path` хранит абсолютный путь (`FileStream.Name`), а не строку, переданную в `Open` — свойство всегда отдаёт однозначный полный путь к открытому файлу.
Шаг 1: `LogFile.Length` запрашивает `RandomAccess.GetLength` при каждом обращении, а не кэширует значение — файл может расти, и будущий tail должен видеть актуальный размер.
Шаг 1: `LogFile.Read` циклически вызывает `RandomAccess.Read`, пока буфер не заполнен или не достигнут EOF — контракт «до заполнения или EOF» не зависит от того, вернул ли один вызов меньше запрошенного.
Шаг 1: тестовые проекты используют xunit 2.x; файлы тестов создаются во временной папке с уникальным именем и удаляются в `Dispose` тестового класса.
Шаг 2: `IndexSnapshot` хранит ссылки на таблицы чанков (`long[][]` и `byte[][]`) и создаётся только в `Publish`; таблица писателя растёт через `Array.Resize`, т.е. копированием ссылок, поэтому ранее опубликованные снимки остаются валидными без блокировок.
Шаг 2: `RaiseLastLevel` пишет уровень через `Volatile.Write`, чтобы повышение уровня было видимо читателям без отдельного изменения `Count`; окончательная публикация всё равно происходит через `Publish`.
Шаг 2: `End` вне диапазона также бросает `ArgumentOutOfRangeException`, как `Offset` и `Level` — единообразная проверка индекса.
Шаг 2: чанк выделяется целиком при первом обращении к нему (589 824 байта: `long[65536]` + `byte[65536]`), что соответствует бюджету 9 байт/запись.
Шаг 3: BOM проверяется отдельным чтением 3 байт при пустом индексе; смещения записей начинаются с 3, но `IndexedLength` остаётся 0, пока не встретится первый `\n`.
Шаг 3: незавершённая строка переносится в начало буфера и перечитывается вместе со следующим блоком; буфер растёт только когда заполнен и не содержит `\n`.
Шаг 3: прогресс считается по байтам до последнего полного `\n` (а не по прочитанным вперёд байтам), в конце принудительно сообщается 100.
Шаг 3: первая строка файла без timestamp создаёт запись `Other` и не проверяется дополнительно на `Exception` — правило 4 имеет приоритет над повышением уровня продолжения.
Шаг 3: несоответствие `start` значению `IndexedLength` — `ArgumentException`; отрицательные значения и `end < start` — `ArgumentOutOfRangeException`.
Шаг 3: при поиске первого токена для `IsExceptionContinuation` токен ограничивается пробелом, табуляцией или `:`, поэтому `NullReferenceException:` и `System.ArgumentException:` распознаются как продолжение исключения.
Шаг 4: исключения выбираются как подмножество ~5% записей с уровнем ERR (20% из них), чтобы не нарушать распределение ~85/10/5; при индексации такие записи повышаются до Exception из-за стектрейса.
Шаг 4: для полной воспроизводимости используется собственный SplitMix64 вместо `System.Random` — реализация `System.Random` может меняться между версиями .NET.
Шаг 4: генерация вынесена в публичный `LogGen.LogGenerator.Generate`; тесты ссылаются на проект `tools/LogGen`, а CLI вызывает тот же метод.
Шаг 4: BOM при `--bom` пишется напрямую в поток до создания `StreamWriter` с UTF-8 без BOM, чтобы BOM присутствовал даже при `--count 0`.
Шаг 5: `LogSession.IndexAsync` запускает индексацию через `Task.Run` с внутренним `CancellationTokenSource`, связанным с переданным токеном; параллельный запуск запрещён (`InvalidOperationException`), после завершения можно продолжить с `IndexedLength`.
Шаг 5: `LogSession.Dispose` отменяет задачу, дожидается её и проглатывает любые исключения индексации, чтобы закрытие приложения не падало; файл освобождается только после завершения задачи.
Шаг 5: `IndexTime` измеряется `Stopwatch` и хранится в тиках через `Interlocked`, чтобы UI мог безопасно читать его после `await`.
Шаг 5: в UI используется `Progress<int>` (обновление прогресс-бара в UI-потоке) и `System.Windows.Forms.Timer` с интервалом 200 мс для `VirtualListSize`; список показывает только заглушки `entry N [level]`.
Шаг 6: `LruCache` с ёмкостью 0 работает как отключённый кэш (не хранит элементы); отрицательная ёмкость — `ArgumentOutOfRangeException`.
Шаг 6: суффикс `… [truncated]` добавляется к полному тексту и к видимому тексту превью; в `FirstLine` он попадает только если обрезка произошла в первой строке.
Шаг 6: ошибки чтения не кэшируются, чтобы после восстановления доступа файл можно было прочитать повторно; выход индекса за диапазон по-прежнему бросает `ArgumentOutOfRangeException`.
Шаг 6: для проверки отсутствия повторных чтений добавлен внутренний счётчик `LogReader.ReadCallCount` и `InternalsVisibleTo("LogViewer.Tests")`; публичный API шага не расширялся.
Шаг 6: `LogSession.Reader` создаётся вместе с сессией; сеттер закрытый, чтобы на шаге 10 можно было заменить reader при reset индекса.
Шаг 7: маппинг `selectedIndex -> entryIndex` реализован тождественным методом `MapToEntryIndex`; подстановка `filterResult.Visible` появится на шаге 9 вместе с фильтрами, которые запрещено делать на шаге 7.
Шаг 7: цвета подсветки хранятся в одной таблице `Dictionary<LogLevel, (Color Back, Color Fore)>`; для Info/Other `BackColor` не задаётся (остаётся прозрачным), чтобы использовать фон `ListView`.
Шаг 7: `CacheVirtualItems` прогревает превью для `StartIndex..EndIndex` через `LogReader.GetPreview`; исключения прогрева проглатываются, так как это оптимизация и не должна ронять отрисовку.
Шаг 7: панель деталей обновляется по `ItemSelectionChanged` и защищена запоминанием последнего показанного индекса — иначе при массовом выделении выполнялось бы чтение на каждое изменение выбора.
Шаг 7: при непрерывном выделении диапазон читается одним `RandomAccess.Read`, если он не больше 64 МБ; для больших диапазонов используется поблочное чтение с потоковым UTF-8 `Decoder`, чтобы не выделять буфер размером с гигабайты (отклонение от буквального «одним Read» только для очень больших выделений).
Шаг 7: разделитель списка и панели деталей (`SplitContainer`) выставляется в `OnLoad` на 2/3 доступной высоты — до создания дескриптора у `SplitContainer` ещё нет реальных размеров.
Шаг 8: `VisibleList` хранит номера записей чанками по 65536 (`int[]`), `Count` публикуется через `Volatile.Write`; `Append` требует строго возрастающих номеров (иначе `ArgumentException`), `RemoveLast` только уменьшает счётчик — это гарантирует корректность бинарного поиска.
Шаг 8: `IndexOfOrNearest` возвращает точную позицию, иначе позицию ближайшей следующей записи, а для номера больше всех видимых — позицию последней; для пустого списка — -1 (нужно для восстановления выбора в шаге 9).
Шаг 8: пустой фильтр возвращает `Visible = null` и `ProcessedCount = index.Count` без чтения файла; фильтр только по уровню вообще не обращается к файлу.
Шаг 8: текстовый проход читает файл окнами по 4 МБ; запись, не поместившаяся в текущее окно, читается отдельно из пула `ArrayPool<byte>`; поиск идёт по первым 256 КБ записи (`TextMaxBytes`) — трактовка «текст проверяется по всей записи (≤ 256 КБ)» как ограничение объёма проверяемого текста.
Шаг 8: регулярное выражение создаётся синхронно в `RunAsync` (не внутри фоновой задачи), чтобы невалидный шаблон сразу бросал `ArgumentException`; `TryValidate` используется UI для подсветки ошибки.
Шаг 8: `RegexOptions.NonBacktracking` создаётся без timeout (движок его не поддерживает), при `NotSupportedException` — обычный движок с `matchTimeout = 1 с`; `RegexMatchTimeoutException` считается несовпадением.
Шаг 8: прогресс — процент обработанных записей; отмена проверяется на каждой записи (чаще, чем требуемый минимум «раз на окно»).
Шаг 8: для приёмки «не читать файл на каждую запись» добавлен внутренний `LogFile.ReadCallCount` и внутренняя перегрузка `FilterEngine.RunAsync(..., int windowSize)`; публичный API шага не расширялся.
Шаг 9: панель фильтров — `FlowLayoutPanel` с `Dock = Top` внутри `SplitContainer.Panel1`; добавлена после списка, чтобы WinForms отдал ей верхнюю полосу, а списку оставил `Fill`.
Шаг 9: debounce-таймер 300 мс; любое изменение ввода дополнительно инвалидирует уже запущенный проход (счётчик `_filterVersion` + отмена `CancellationTokenSource`), поэтому устаревший результат не применяется даже если успел досчитаться.
Шаг 9: результат применяется только при совпадении версии и той же сессии; продолжение после `await` выполняется в UI-потоке, `Progress<int>` создаётся в UI-потоке.
Шаг 9: при невалидном regex фильтр не применяется (остаётся предыдущий результат), `TextBox` получает фон `#FFCDD2`, tooltip с текстом ошибки и статус `Invalid regex`; ошибка сбрасывается при следующем изменении ввода.
Шаг 9: статус во время прохода — `Filtering… P%`, после — `Shown: M of N`; для пустого фильтра `Visible = null` и `Shown: N of N`.
Шаг 9: выбор восстанавливается по первой выделенной записи через `IndexOfOrNearest` с ограничением последней видимой записью и `EnsureVisible`; панель деталей обновляется явно, чтобы не зависеть от события смены выбора.
Шаг 9: при активном фильтре `MapToEntryIndex` возвращает -1 для позиции вне `Visible` (вместо подстановки сырого индекса), а копирование в буфер уже использует этот маппинг из шага 7.
Шаг 9: если фильтр был активен во время индексации, после успешного завершения индексации он применяется заново к выросшему индексу (не tail, а согласование снимка); при открытии нового файла фильтр сбрасывается в «все уровни, пустой текст, без regex».
Шаг 9: у поля текста задан `AccessibleName = "Text filter"` — для доступности и UI-автоматизации.
Шаг 9: ручная проверка на `--count 1000000`: снятие `ERR` — 381 мс (включая 300 мс debounce), возврат всех уровней — 338 мс; статус `Shown: 959688 of 1000000` и `Shown: 1000000 of 1000000`.
Шаг 10: `LogSession.PollAsync` опрашивает изменение размера файла и первых 256 байт; при росте возвращает `Grown` и доиндексирует файл, при уменьшении/изменении заголовка возвращает `Reset`, инкрементирует `Generation`, создаёт новые `LogIndex` и `LogReader` и переиндексирует файл заново.
Шаг 10: `FilterEngine.ExtendAsync` производит инкрементальную фильтрацию новых записей и обновляет совпадение для усечённой/дописанной последней записи, используя общую функцию проверки `MatchesEntry`.
Шаг 10: `LogGen generate --follow` дописывает файл в режиме реального времени, включая неполные строки с принудительным `writer.Flush()` и автоусечение `--truncate-every-sec`.

Шаг 11: `EntryPreview` расширен полями `Timestamp`, `Level`, `Component`, `Message` вместо одного `FirstLine`; парсинг выполняется один раз в `GetPreview` и кэшируется в LRU.
Шаг 11: `MainForm` использует 4 колонки (`Time`, `Level`, `Component`, `Message`) с `SubItems`; подсветка остаётся на всю строку (перенос на OwnerDraw отложен на шаг 13).
Шаг 11: ширина колонок сохраняется в `%AppData%\7DTDLogViewer\settings.json` (`{ "columnWidths": [...] }`), загружается при старте, сохраняется при `FormClosing`; ошибки чтения/записи игнорируются.

Шаг 12: у `LogFilter.Excludes` добавлено значение по умолчанию `null` — 16 существующих мест создания фильтра (тесты) не изменились; движок нормализует null в «нет исключений». Публичный API обратно совместим.
Шаг 12: excludes проверяются в общем `MatchesEntry` (OrdinalIgnoreCase) перед текстом; совпадение любой строки-исключения убирает запись из результата.
Шаг 12: если Excludes не пуст, а Text пуст — проход идёт по текстовому пути (`RunWithText`), так как проверка исключений требует чтения файла; чисто уровневый путь (`RunLevelOnly`) используется только без excludes.
Шаг 12: контекстное меню списка («Exclude this message» / «Exclude this component» / «Clear all excludes»); исключение сообщения берётся из `EntryPreview.Message` и обрезается до 100 символов (`ExcludeMaxLength`), чтобы не хранить гигантские стектрейсы.
Шаг 12: excludes сохраняются в тот же `settings.json` (`"excludes": [...]`) и переживают перезапуск; счётчик виден в статус-баре `[Excludes: N]`.

# Smoke test и общие соглашения (не относится к конкретному шагу)

Smoke test: `tests/LogViewer.Tests/PlayerLogTests.cs` индексирует `samples/Player.log` и проверяет инварианты (`Other < 2%`, `End(i) > Offset(i)`, `End(last) == IndexedLength`, `IndexedLength == File.Length`). Это НЕ часть workflow шагов 1–10, а защита от регрессии индексатора. При выполнении шагов 4+:
- не изменять `samples/Player.log`;
- не удалять, не переименовывать и не «улучшать» `PlayerLogTests.cs`;
- не использовать `samples/Player.log` как цель для `LogGen generate` (использовать отдельный путь в `samples/` или временную папку);
- если тест упал — сообщить в отчёте, не пытаться «исправить» его самостоятельно.
